# Design

## Context

`models/` holds OpenVINO IR exports (one folder per model, `openvino_model.xml/.bin`, tokenizers, `config.json`, etc.). Three models are already published under https://huggingface.co/m4gshm and serve as the pattern for model cards. No publishing automation exists. Repo uses root-level Python scripts and `uv`/`task` (see `Taskfile.yml`).

## Goals / Non-Goals

**Goals:**
- One script, `publish_models.py` at repo root, runnable as `python publish_models.py` (or via a task).
- Explicit `MODELS` list inside the script — the single place to edit.
- Idempotent sync via `huggingface_hub.upload_folder` (it hashes files and skips unchanged uploads).
- **Reuse, don't duplicate**: model cards are generated by the existing `models/gen_readmes.py` (the generator of the 3 already-published cards), not by a new template.

**Non-Goals:**
- Auto-discovering all of `models/` (list stays explicit by request).
- Deleting remote files that vanished locally (sync never deletes).
- Private repos, gated repos, organizations other than `m4gshm`.
- Downloading models from HF (out of scope; separate concern).

## Decisions

1. **`huggingface_hub` with `upload_folder(..., repo_id="m4gshm/<name>")`** over raw git LFS or `huggingface-cli upload`: Python API is scriptable, handles repo creation (`create_repo(repo_id, exist_ok=True)`), commit messages, and change detection. Alternative `huggingface-cli upload <repo> models/<name> .` per model is shell-heavy and harder to extend with card generation.
   - `upload_folder` default behavior re-commits changed files and skips identical ones → satisfies the sync requirement with no custom hashing.
2. **Model list as a Python constant** (`MODELS: list[str]`) in the script — simplest extension point, matches "список может пополняться". A separate YAML config was rejected as extra machinery for one list.
3. **Reuse the existing generator `models/gen_readmes.py`** — it already produced the 3 published cards (template: YAML front matter with license/base_model/tags, quantization summary derived from folder name + `openvino_config.json`, modality table, file list). The publish script imports it and runs its logic for listed folders lacking a README, instead of keeping a second template copy. One small fix needed there: replace the `<org>` placeholder in the code example with the real org (`m4gshm`).
4. **Remote card wins**: an existing README is never overwritten locally, and if the remote repo already has a `README.md`, it is excluded from the upload (`ignore_patterns`). This prevents weak cosmetic diffs on re-runs of the already-published models; substantial card updates go through HF or a manual upload.
5. **`.gitattributes`**: rely on HF's automatic LFS tracking for `*.bin` on repo creation; no local `.gitattributes` upload needed.
6. **Auth**: read `HF_TOKEN` env var, fall back to the cached token (`HfFolder`/`whoami`). Fail fast with a clear message before touching anything.
7. **Continuable on errors**: a missing folder or failed upload logs and moves to the next model; exit code is non-zero if any model failed.
8. **Dependency**: add `huggingface_hub` to both root `pyproject.toml` and `agent/pyproject.toml` (per repo rule: runtime deps must be in both).
9. **Tests**: `publish_models_test.py` co-located, covering list parsing, quantization/config extraction for the card, and the missing-folder / existing-README branches, with the HF client mocked.

## Risks / Trade-offs

- [Large uploads interrupted] → each model is a separate commit; a failed model can be retried by re-running (idempotent).
- [Card metadata guessed from folder name] → template keeps quantization description conservative; user edits README manually, script respects it (decision 4).
- [HF rate limits / token scope] → clear per-model error output naming the failed repo.
