# Design

## Определение сессии

OpenAI-протокол stateless: каждый запрос повторяет всю историю диалога. Сессия = цепочка запросов, где история каждого следующего — расширение истории предыдущего.

- **Реестр сессий** (`agent/openai/session_registry.py`): список активных сессий; для каждой — канонический список «отпечатков» сообщений.
- **Отпечаток сообщения**: устойчивый хеш канонического представления message (role + сериализованный content: текст, tool_calls, media-дескрипторы). Для медиа в base64 хешируется само содержимое (детерминированно).
- **Префиксное сопоставление**: для каждой сессии хранятся кумулятивные хеши префиксов истории (hash сообщений 0..k). Входящий запрос: вычислить кумулятивные хеши своей истории и найти сессию, чья цепочка хешей является префиксом входной. Совпадение с точностью до «продолжения» — та же сессия; новая история — новая сессия.
- **Ограничения**: реестр живёт в памяти процесса (перезапуск сервера = все сессии новые, fallback не нужен — просто новые сессии). Верхний лимит активных сессий (например 50, LRU-вытеснение самых старых) — защита от роста памяти на длинных прогонах.
- **Клиентский фильтр**: определение включено только для opencode. Признак — `user-agent` содержит `opencode` (проверить реальный заголовок в http.log; при необходимости уточнить). Прочим клиентам сессия не определяется.

## Маршрутизация логов

Текущий `dictConfig` статичен на запуск сервера. Папка сессии известна только при обработке запроса, поэтому:

- **SessionDispatchHandler**: единый handler-диспетчер, подключённый вместо прямых file-handler'ов для `http`, root (`app.log`) и generated-логгеров. По `contextvar current_session` (устанавливается на время обработки запроса) пересылает запись в FileHandler соответствующей сессии; без сессии — в file-handler папки запуска (как сейчас). Handlers сессий создаются лениво, один набор на сессию (`app.log`, `http.log`, `out.log` в папке сессии), реестр handler'ов живёт рядом с реестром сессий.
- Формат и ротация — те же (RotatingFileHandler, 10 MB), что и сейчас.
- `current_session` — `contextvars.ContextVar`, выставляется в общей точке входа chat-запроса (`engine_rest_common`) и сбрасывается после; streaming и thread-pool исполнение инференса должно видеть значение (прокинуть контекст в worker-поток, где это уже требуется для других contextvar'ов — проверить, как передаётся контекст в ThreadPoolExecutor).

## dialog.log

- Пишется кодом обработки запроса, а не через logging handler: в точке входа, после определения сессии, в `dialog.log` сессии дописываются только новые сообщения истории (сравнение по числу уже записанных сообщений сессии — реестр хранит `logged_count`; расхождение истории с recorded префиксом исключено самим определением сессии).
- Сгенерированный ответ дописывается после завершения инференса (там же, где сейчас пишется `result:` / outbound).
- Формат: по записи на сообщение с разделителем и ролью, UTF-8; thinking (reasoning_content) — в dialog.log не включать (он и сейчас уходит в generated-поток отдельно; при необходимости можно пересмотреть).
- Для неопределённой сессии dialog.log не пишется; prompt.log убирается полностью (logger `agent.inference.prompt` и его handler удаляются из dictConfig).

## Папки

```
logs/<model>/<run-ts>/                     # как сейчас, fallback-логи
logs/<model>/<run-ts>/sessions/<YYYY-MM-DD_HH-MM-SS>_<id8>/
    app.log  http.log  out.log  dialog.log
```

`<id8>` — короткий отпечаток первой истории (стабильный, различимый).

## Риски / решения

- **ThreadPoolExecutor и contextvar**: если контекст не пробрасывается в поток инференса, часть логов уйдёт в fallback. Проверяется тестом; при необходимости — явная передача session в worker.
- **Ветвящиеся истории** (retry/regenerate: общий префикс, потом расхождение): по определению расхождение = новая сессия, хотя семантически это «ветка» того же диалога. Для первой имплементации принимаем: ветка — отдельная сессия (у пользователя такое поведение opencode создаёт и так новый диалог с частичным префиксом). Отмечено как известное ограничение.
- **Медиа в истории**: большие base64-хеши считаются один раз и кешируются по индексу сообщения; стоимость сопоставления O(сообщений запроса).
- **Порядок логов**: сессия выставляется до первого лога обработки запроса и сбрасывается в finally — иначе часть записей уйдёт в общий app.log; это допустимо (fallback = «как сейчас»).
