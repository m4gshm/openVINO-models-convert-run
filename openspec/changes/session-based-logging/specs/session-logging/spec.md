# Spec Delta

## Purpose

Группировка логов сервера по клиентским сессиям: все записи, относящиеся к одному диалогу клиента, попадают в отдельную папку с полным логом диалога, чтобы диалог можно было восстановить и читать целиком.

## ADDED Requirements

### Requirement: Определение клиентской сессии
Система SHALL определять клиентскую сессию входящего chat-запроса по истории сообщений: запрос, чьи messages совпадают по префиксу с уже виденной историей известной сессии, MUST относиться к этой сессии. Запрос с историей, не совпадающей ни с одной известной сессией, MUST открывать новую сессию. Определение применяется ко всем chat-запросам с непустой историей сообщений независимо от клиента.

#### Scenario: Продолжение диалога
- **WHEN** приходит запрос, чья история messages расширяет историю уже известной сессии
- **THEN** запрос относится к этой сессии

#### Scenario: Новый диалог
- **WHEN** приходит запрос с историей, не совпадающей по префиксу ни с одной известной сессией
- **THEN** открывается новая сессия

### Requirement: Папка логов сессии
Когда сессия определена, все логи запроса MUST писаться в папку сессии `logs/<model>/<timestamp-запуска>/sessions/<YYYY-MM-DD_HH-MM-SS>_<session-id>/`, где дата-время — момент первого сообщения сессии. Когда сессия не определена, логи MUST писаться в папку запуска как раньше.

#### Scenario: Первое сообщение сессии
- **WHEN** для запроса открыта новая сессия
- **THEN** создаётся папка сессии, имя которой начинается с даты и времени этого (первого) запроса

#### Scenario: Все логи внутри папки сессии
- **WHEN** запрос относится к определённой сессии
- **THEN** его http-лог, лог сгенерированного вывода и application-лог пишутся в файлы внутри папки этой сессии

### Requirement: Единый лог диалога
Для каждой определённой сессии система MUST вести `dialog.log` — единый последовательный лог диалога, содержащий входящие сообщения и сгенерированные ответы в порядке их появления. Повторно присылаемая в каждом запросе старая часть истории MUST логироваться только один раз: при обработке запроса в dialog.log дописываются только новые сообщения, которых там ещё нет.

#### Scenario: Инкрементальная запись входящих
- **WHEN** приходит запрос, чья история содержит сообщения, уже записанные в dialog.log сессии
- **THEN** в dialog.log дописываются только новые (ещё не записанные) сообщения

#### Scenario: Ответ попадает в диалог
- **WHEN** генерация ответа для запроса сессии завершена
- **THEN** сгенерированный текст дописан в dialog.log сессии после входящих сообщений

### Requirement: prompt.log упраздняется
Система MUST прекратить запись prompt.log (полные повторяющиеся промпты каждого запроса). Роль файла с входящими сообщениями берёт dialog.log из предыдущего требования.

#### Scenario: prompt.log не создаётся
- **WHEN** сервер обрабатывает запросы
- **THEN** новый prompt.log не создаётся и не наполняется

### Requirement: Fallback-логирование без сессии
Система MUST логировать как раньше (в общие файлы папки запуска, без папки сессии) всё, к чему определение сессии неприменимо: запросы без истории сообщений (text completions, Ollama generate), логи вне обработки запросов (запуск, загрузка модели, фоновые события), запросы с пустой историей, а также chat-запросы, чью историю сопоставить не удалось. Существующее поведение при этом не меняется.

#### Scenario: Неопределённая сессия
- **WHEN** запрос не удалось отнести к сессии
- **THEN** его логи попадают в общие файлы папки запуска, как до введения сессий
